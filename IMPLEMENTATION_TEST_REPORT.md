# Rider Booking Frontend — DB/API Integration Report

## What was changed

Both mobile apps were updated to use the documented deployed API rather than local dummy data.

### Rider app
- `/api/profile/me` is the source of rider/account data.
- `/api/profile/me/rides` drives History, Deliveries, recent rides and ride details.
- `/api/profile/me/active-ride` restores an active ride after app restart.
- `/api/profile/me/invoices` drives Earnings.
- `/api/profile/me/rider-location` drives the rider's saved location/verification screens.
- `/api/profile/me/verification-details` drives the rider verification status screen.
- `/rider/status` controls AVAILABLE/OFFLINE.
- `/rider/save/location` is used before an assignment.
- `/rider/fetch/livelocation` is used only for ACCEPTED/STARTED rides.
- Rider WebSocket subscription uses `/topic/rider/{riderId}` for requests/cancellation events.
- Background live GPS uses the Expo location task and sends only latitude/longitude.
- Accept, OTP start, rider cancel and end ride call the documented lifecycle endpoints.
- Local active-ride state is cleared after completion/cancellation/logout.

### Admin app
- `/api/profile/me` drives the admin profile.
- `/api/profile/me/rides` drives Collection, Inventory and recent rides.
- `/api/profile/me/invoices` drives admin invoice/revenue totals.
- `/api/profile/me/active-ride` drives the live ride monitor.
- `/ride/request` is the only ride-creation write.
- Admin live tracking uses the private STOMP destination `/user/queue/ride/{rideId}/location`.
- Admin verification screen uses:
  - `POST /rider/{riderId}/verification-details`
  - `GET /rider/{riderId}/verification-details`
  - `PATCH /rider/{riderId}/verification?verified=...`
- Hardcoded Google Places API key was removed. Pickup/destination lookup now uses Expo geocoding.
- Random fare fallback was removed. If the backend fare endpoint returns a numeric fare, it is used. If the current placeholder endpoint does not return a usable number, the admin must enter the approved fare manually before sending the request.

## Important backend limitations preserved intentionally

The technical reference does NOT define a separate inventory table/API. Therefore the admin inventory screen is backed by `RIDE_DETAILS` records (vehicleName/chassisNo/status), rather than inventing an inventory endpoint.

The reference assigns KYC/verification submission and approval to the admin workflow. The rider app therefore reads its verification status instead of pretending that a rider-owned KYC write endpoint exists.

The current `/api/fare/calculate` endpoint is documented as a placeholder and must not be used as a production invoice calculation. No random/static fare is generated by this frontend.

The reference also documents that `/login` is currently protected by SecurityConfig and can return 403 before the controller. The frontend tries the real `/login` first and uses the documented `/sendJWT` development fallback only while `EXPO_PUBLIC_ALLOW_DEV_JWT_LOGIN` is not set to `false`.

## Validation performed

- Parsed all JS/JSX/TS/TSX source files with the TypeScript transpiler: 0 syntax errors.
- Checked all relative imports in both projects: 0 missing relative imports.
- Scanned active source for DummyData, Math.random-generated records, hardcoded bike arrays and hardcoded document arrays: none in the active app flow.

## End-to-end test order

1. Confirm ADMIN and RIDER accounts exist.
2. Confirm rider profile exists through `POST /rider`.
3. Admin saves rider verification details and sets `verified=true`.
4. Rider gets a fresh GPS point through `/rider/save/location`.
5. Admin creates `/ride/request`.
6. Rider receives `RIDE_REQUEST` on `/topic/rider/{riderId}`.
7. Rider accepts.
8. Admin subscribes to `/user/queue/ride/{rideId}/location`.
9. Rider sends `/rider/fetch/livelocation`.
10. Rider verifies the 4-digit start OTP.
11. Rider ends the STARTED ride.
12. Confirm ride becomes COMPLETED, rider becomes AVAILABLE, and one PENDING invoice exists.

## Security notes

Do not put JWTs, KYC values, bank details or database credentials into source control, screenshots or logs. Use secure storage for mobile JWTs. The documented `sendJWT` fallback should be disabled once the backend `/login` configuration is intentionally made public and properly secured.
